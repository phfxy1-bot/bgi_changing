# 委托机制泛化方案（可调用实施计划）

状态：P0 脚手架已就绪，待样本与模型通道；尚无准确率结论，未进入 P1。目标是用“事件级推理”替代内容库中的语义部分，把版本维护依赖从“每个委托”降到“每种机制”。

## 1. 核心判断

内容数据由两类信息组成，替代性不同：

| 组成 | 能否被推理模型替代 | 替代方案 |
|---|---|---|
| 语义流程（这个委托要做什么） | **能** | 面板文本 + 截图 → 机制类型 → 机制模板 |
| 空间路径（具体怎么走到那） | **不能** | 通用导航：追踪图标视觉伺服 + 局部重规划 |

因此本方案成立的前提是：**语义层交给模型，空间层交给导航**。两者都不依赖“具体某一委托”，新委托若属于已知机制则无需新增内容。

## 2. 非目标

- 不把推理模型放进逐帧控制循环（延迟量级不允许）。
- 不追求“完全零内容库”。内容库保留为第一优先命中路径。
- 不做在线自动探索建图（离线任务，成本远高于收益）。

## 3. 架构：四层优先级

```
委托面板读取（OCR + 截图）
   ├─ ① 内容库精确命中 ────────→ 直接执行（0 额外延迟，最稳）
   ├─ ② 语义泛化（推理模型）────→ mechanism + 参数
   │        └→ 机制模板：dialog / combat / collect / escort / timed / photo / music / other
   ├─ ③ 通用导航 ──────────────→ 追踪图标视觉伺服 + 局部重规划
   └─ ④ 兜底 ──────────────────→ 放弃该委托 → 记录 → 下一个
```

执行层必须保持确定性：模型只决定“做什么”，`PathExecutor` 负责“怎么动”。

## 4. 机制模板与动作原语

模板是“骨架 + 参数”，不含坐标：

```json
{
  "mechanism": "escort",
  "confidence": 0.86,
  "params": { "target": "npc", "time_limit": 180, "combat": true }
}
```

约束：

1. 输出必须是**封闭枚举**的 mechanism 与受控参数，禁止自由文本。
2. mechanism → 模板的映射表集中维护，未知 mechanism 一律走第 ④ 层。
3. 模板只能使用现有动作原语（路线动作 + 键鼠 + JS 交互）；缺少的原语按“新增动作实现”立项，一次投入全局复用。

## 5. 阶段计划

### P0 离线可行性验证（无代码改动）

- 产出：30~50 条真实委托样本（描述文本 + 面板截图 + 现场截图）、人工机制标注表、VLM 分类结果与混淆矩阵。
- 验收：机制分类准确率 ≥ 90% 进入 P1；70%~90% 需补视觉输入后重测；< 70% 停止本方案。
- 说明：这一步可在一天内否定整个路线，成本最低，必须先做。

### P1 面板读取与样本管线

- 产出：稳定的“委托面板 → 结构化对象（名称/地区/描述/进度 n/4）”读取；样本采集工具（截图与文本落盘）。
- 参考实现：`js/AutoCommissionNova/src/config/game-constants.js` 的 OCR 区域与 `commission-scanner.js`。
- 验收：连续 20 次读取零失败；分辨率切换后可通过配置适配。
- 失败处理：读取失败 → 回落人工模式并记录样本。

### P2 机制模板与动作原语

- 产出：mechanism schema、模板映射表、3 个骨架模板（dialog / combat / collect）端到端跑通（建议选挪德卡莱）。
- 验收：3 个模板在真实委托上成功率 ≥ 90%，且不依赖具体委托坐标。
- 失败处理：模板内步骤失败时能回退到 ① 或 ④。

### P3 泛化闭环

- 产出：②→模板→③→校验→回面板的完整链路；置信度门控；决策日志（输入文本、截图、模型输出、置信度、耗时）。
- 验收：未收录委托（属于已知机制）执行成功率 ≥ 80%；单委托平均耗时 ≤ 人工版本 1.5 倍；每委托模型调用 ≤ 3 次；误判导致卡死率 ≤ 5%。
- 失败处理：低置信度直接走第 ④ 层，不硬跑。

### P4 导航通用化（依赖项目记忆方向四 / 六）

- 产出：追踪图标视觉伺服的稳定性提升；卡死检测由 1 秒采样改为高频判定；简单局部重规划。
- 挂载点：`GameTask/AutoPathing/PathExecutor.cs`（定位、卡死检测、转向）、`TrapEscaper`。
- 验收：因“找不到目标 / 卡住”导致的失败占比下降 50%。
- 说明：本阶段必须改主程序；P1~P3 建议放在脚本层，便于快速迭代且不涉及主仓库合并。

### P5 运维与内容策略

- 产出：模板版本化、失败聚类报告、模板与特定流程的发布边界。
- 与 `gated-content-distribution.md` 对接：机制模板与动作原语公开（代码/骨架），具体坐标与特殊流程按审批分发。

## 6. 指标汇总

| 指标 | 目标 |
|---|---|
| 机制分类准确率 | ≥ 90% |
| 未收录委托（已知机制）成功率 | ≥ 80% |
| 单委托耗时 | ≤ 人工版本 1.5 倍 |
| 模型调用次数 | ≤ 3 次/委托 |
| 误判卡死率 | ≤ 5% |
| 新委托内容新增量 | 已知机制 0；新机制 1 个模板 |

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 描述不足，纯文本无法判断机制 | 准确率不达标 | 多模态输入（面板 + 现场截图） |
| 模型输出不稳定 | 不可复现，用户不信任 | 置信度门控；执行确定性；决策日志 |
| 导航通用化难度被低估 | 成功率卡在 P3 | 内容库继续兜底；优先覆盖高频机制 |
| 新机制需要新动作原语 | 出现代码依赖 | 原语一次投入全局复用，按需立项 |
| 成本失控 | 每委托多次调用 | 每日预算上限；命中内容库优先 |

## 11. T 轨道：任务变更驱动（QuestWatch）

### 11.1 现状缺口

### 11.2 设计：四个组件

```
1Hz 截图/OCR → QuestWatch      任务栏 + 交互提示文本指纹
                    │ 变化事件 {text, distance, signature}
              ObjectiveParser   关键词 → 目标类型（封闭枚举）
                    │ {type, target, distance}
              ObjectiveRunner   追踪 + 导航 + 到点交互
                    │ 成功 / 超时
              Director          与 step 列表融合、超时与放弃
```

目标类型枚举（v1 关键词表，封闭集合）：

| 文本特征 | type | 动作 |
|---|---|---|
| 前往 / 到达 / 移动至 + 距离 | navigate | V 追踪 → 图标伺服 → 距离 ≤3m 停止 |
| 与…对话 / 交谈 | talk | 导航到 NPC 图标 → F → 交给 AutoSkip |
| 跟随… | follow | 低速跟随图标，保持 5~10m |
| 击败 / 消灭 / 清理 | combat | 调 AutoFight，结束后等文案变化 |
| 收集 / 获取 N 个 | collect | 导航 + AutoPick 循环 |
| 调查 / 搜寻 / 查看 | interact | 导航 + F |
| 无匹配 | unknown | 记录样本，可选交给 LLM，否则放弃 |

关键规则：

1. 采样 1Hz；文本归一化（去空白、数字统一为 `#`）后取指纹；连续 2 次相同才确认变化，避免动效抖动。
2. 只做事件级判断，不进逐帧回路；v1 模型调用为 0，unknown 分支最多 1 次可选 LLM 调用。
3. 优先级：`process.json` 命中 > QuestWatch；QuestWatch 仅在"未编排或出现新目标"时接管。
4. 超时：单目标 180s 无变化 → 重读面板；连续 2 次失败 → 放弃该委托回到面板（第 ④ 层）。
5. 对话结束判定看"交互提示消失 + 任务栏文本变化"，不用固定秒数。

### 11.7 长线任务适配：传送、卡死恢复与对话推进（Q1/Q2）

适用范围调整：T 轨道的首要目标从“每日委托”改为**长线剧情任务**（主线、传说、世界任务）。委托流程短、同区域，长线任务跨区域、几十步，差异集中在三处，Q1/Q2 针对这三处补齐。

#### 11.7.1 传送：候选序列而不是“最近一个”

追踪栏距离是**直线距离**，只能用于“要不要传送”，不能用于“选哪个传送点”。选点依据是：任务追踪开启时打开大地图，**地图中心即任务点**，按每个传送点图标到中心的像素距离排序。流程：

1. 距离 > 150 m 且追踪图标持续 8 s 不可见 → 打开大地图；
2. 点击右下角“切换追踪”两次，确保任务点居中；
3. 全图模板匹配传送点（`TeleportWaypoint` / `StatueOfTheSeven` / `Domain`），按到中心的像素距离排序；
4. 逐个点击候选，每次 2.2 s 后检测地图是否关闭；未关闭则原地二次点击，仍未关闭换下一个候选。**前提是 BGI 已开启「快速传送」**——官方文档说明，未开启时点击传送点只会弹出传送点列表，需人工点“传送”，脚本无法完成闭环；
5. 单个目标最多传送 2 次，同一像素桶（40 px）内的传送点不重复尝试。

**关键修正**：最近的传送点未必可达（可能隔着山或断崖），因此候选按距离排序后允许“失败则换下一个”，并记录已用点，避免传送—卡住—再传送的死循环。

落地代码：`teleportToQuest()`、`ensureReachable()`（`js/quest-watch/objective-runner.js`）；图标素材复制自主程序 `QuickTeleport/Assets/1920x1080`，存放于脚本内 `Data/MapChooseIcon/`（脚本只能读自己的工作目录）。

#### 11.7.2 卡死检测与侧移恢复

距离在 `8 s` 内没有缩短 ≥ `3 m` 视为卡住，处置顺序为：侧移（左右交替转 35° 后前进 1.4 s）→ 累计 4 次仍无进展则返回 `stalled`，由上层换传送点或计入失败预算。跟随/护送类目标不传送、不跳跃。

#### 11.7.3 连续对话推进

原实现只在进入对话后点一次选项，长线任务的对话会停在半途。

经核对官方文档，BGI 内置「自动剧情」（AutoSkip）已具备：识别隐藏 UI 按钮判断对话、空格跳过文本、自动选择选项（默认最后一项，支持 `select_options.json` 优先选择）、3 秒内弹窗自动关闭、提交物品自动提交。若脚本再自行点击，会与它抢操作、选项选择也可能矛盾。

因此默认把对话交给自动剧情（`delegate_dialogue=true`）：`talk` 目标到达后，QuestWatch 只调 `waitDialogueEnd()` 观察气泡消失（连续 3 次不可见判定结束，兼容过场黑屏），不点击任何选项；对话结束、任务栏目标变化后由 watch 接管。关闭自动剧情时把 `delegate_dialogue` 设为 `false`，回退到自带的 `advanceDialogue()`（有选项按目标名匹配、否则选第一项，无选项点屏幕下部推进）。

注意自动剧情的“默认暂停”名单（凯瑟琳、铁匠等）会让这些 NPC 的对话不被跳过，遇到时表现为对话超时，需人工点掉。

#### 11.7.4 边界与验证

- 解谜、机关、限时挑战不具备通用解法，仍由“放弃并提示人工”兜底；
- 目标定在 80% 的步骤可自动完成，不追求 100%；
- 验收：Q1 在跨区域任务上完成“传送 → 落地 → 走到目标”；Q2 在长对话任务上完成“推进到底 → 新目标接管”。
