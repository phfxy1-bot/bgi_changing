# 敏感内容的分级与授权分发（设计草案）

状态：草案，未实现。本方案作用在**内容数据与资产**层（路线文件 `pathing/*.json`、流程文件 `process.json`、模型权重、策略文本等），不作用在程序代码层。

## 1. 目标

- 让外部**知道**这类能力存在（格式、规范、获取方式），但不公开可直接运行的内容。
- 只有**经管理员审批**的用户才能获取并使用。
- 授权可撤销、可审计。
- 主程序保持完全开源、可用，不因授权状态被削弱。

## 2. 非目标

- 不做强 DRM，不假设能阻止已授权用户的二次传播。
- 不用密码包、客户端硬编码校验等"看起来安全"的方案。
- 不把任何主程序功能锁在授权之后（与 GPL-3.0 冲突）。

## 3. 分层前提：程序、资产、内容、文档

本方案成立的前提是先把"被授权的东西"和"公开的东西"分开。四类对象，四套规则：

| 对象 | 具体是什么 | 适用许可 | 谁能拿到 |
|---|---|---|---|
| **程序代码** | `.cs` / `.xaml` / `.csproj` | GPL-3.0 | 所有人，包括任意 fork |
| **资产** | ONNX 权重、训练数据、标注集 | 可单独设定（可私有） | 按资产许可 |
| **内容数据** | 路线 JSON、`process.json`、战斗策略文本 | 可单独设定（可授权） | 审批通过的协作者 |
| **文档** | `Docs/**/*.md`（含本草案） | 随主仓库 → GPL-3.0 | 所有人 |

两条关键事实：

1. **模型权重不在代码仓库里。** `BgiOnnxModel` 中所有模型都是 `Assets\Model\...` 下的文件，通过 `Global.Absolute(ModelRelativePath)` 在运行时加载，由 `BetterGI.Assets.*` 外部 NuGet 包提供。因此权重属于"资产"，不属于"程序代码"，不受 GPL 约束。
2. **fork 只复制代码，不复制资产与内容。** 任何人 fork 主仓库，拿到的是框架；私有仓库里的路线与私有包里的权重不会随 fork 扩散。

由此得出的结论：

- 程序改进（本备忘录方向一、三、四、五）一旦合入，就是 GPL 的一部分，**无法形成独占壁垒**，第三方可 fork 并自行实现同等功能。
- 可形成差异的是**资产质量**（模型权重、训练数据）与**内容**（路线、流程），它们与本方案的授权通道对应。
- 因此策略是：**代码开放（可回馈上游），资产与内容私有（按需授权）**。

## 4. 决策：为什么不用"解压密码"

| 事实 | 后果 |
|---|---|
| 客户端必须能解密，密钥必然存在于客户端或由用户输入 | 任一授权用户都能拿到明文 |
| 本项目为 GPL-3.0 本地客户端，允许用户修改代码 | 任何客户端校验都可被移除 |
| 密码无法撤销、无法审计、无法限定范围 | 泄漏后无法定位来源 |

结论：加密只降低"随手转发"的概率，不构成访问控制。真正的控制点在**分发通道**（谁能从哪个地址拉到文件）。

## 5. 内容分级

| 级别 | 内容示例 | 公开程度 | 分发通道 |
|---|---|---|---|
| L0 公开 | 格式说明、能力说明、最小示例 | 完全公开 | 官方脚本仓库 |
| L1 审批可见 | 完整流程文件、开荒路线 | 说明公开，内容私有 | 私有 Git 仓库，人工加 collaborator |
| L2 小范围 | 高风险或快速失效的内容 | 不公开 | 私有 Release 资产 / 短时签名 URL |

分级依据是"泄漏代价"，不是"技术难度"。

## 7. 分阶段落地

### Phase 1：无代码改动（先验证需求）

- L1 内容放**私有仓库**，审批后把用户加为 collaborator。
- 用户用标准 git 凭据（PAT / SSH）正常 clone；BGI 侧用现有"自定义仓库 URL"或本地仓库导入即可。
- 撤销 = 移除 collaborator；审计 = 仓库成员与提交记录。

这一阶段能回答"需求是否真实、审批流程是否可承受"，且改动为零。

### Phase 2：程序支持私有源（如确有需要）

1. `ScriptRepositoryRemote` 增加 `CredentialRef`（指向系统凭据管理器条目，如 Windows Credential Manager）。
2. 新增 `Kind = "gated"`：`RefreshLocalRepositoryAsync` 与 `EnsureOfficialRepositoryAsync` 之外，新增 `EnsureGatedRepositoryAsync`。
3. 授权缺失时：仓库出现在列表中但显示"未授权"，不参与内容索引；给出申请入口。
4. 凭据错误/过期：不自动重试，给出明确提示。
5. 内容来源标记写入 `ScriptRepositoryRegistration` 或旁挂索引，用于追溯。

注意：这一段代码合入后即为 GPL 的一部分，第三方 fork 可以删除校验。它的价值是引导、记录与减少误用，安全边界仍在私有仓库凭据。

### Phase 3：授权服务（可选）

服务端维护用户 ↔ 内容版本 ↔ 有效期；客户端凭令牌换取短时签名 URL。适用于需要自动过期与细粒度回收的场景，代价是需要持续运维。

## 8. 授权文件草案（Phase 2）

```json
{
  "schema": 1,
  "subject": "<用户标识>",
  "repositories": [
    { "repository_id": "repo_gated_story", "granted_version": 3, "expires_at": "2027-01-01T00:00:00Z" }
  ],
  "issued_by": "<管理员标识>",
  "issued_at": "2026-11-18T00:00:00Z"
}
```

说明：该文件只是**客户端侧的门槛凭据**，不是安全边界；其价值在于"撤销与审计"，安全边界仍是私有仓库的凭据。

## 9. 授权流程

```
用户提交申请（说明用途、已有 UID / 使用记录）
  → 管理员审核
  → 加入私有仓库 collaborator（或在授权服务中签发令牌）
  → 客户端拉取内容（Phase 1：git 凭据；Phase 2：gated 源）
  → 内容使用；客户端记录已获取版本
撤销：移除 collaborator / 令牌失效 → 客户端下次刷新失败
```

## 10. 安全与合规边界

1. **GPL-3.0**：不得对主程序附加"仅授权者可用"的限制，也不得因授权状态拒绝提供源码。授权只作用于**资产与内容数据**。
2. **内容许可**：路线/流程数据单独声明许可与分发条款（例如"仅限授权用户使用，禁止再分发"）。
3. **可追溯**：每份授权内容带版本号；可选对导出文件打来源标记，便于定位泄漏源。
4. **不承诺保密**：文案中明确"授权内容可能被二次传播"，避免给出不实的安全承诺。

## 11. 失败与撤销

| 场景 | 行为 |
|---|---|
| 授权过期 | 仓库标记为未授权，已下载内容不自动删除（用户可继续本地使用） |
| 凭据失效 | 明确提示重新授权，不静默重试 |
| 内容版本变更 | 已获取版本与新版本不一致时提示，由用户决定是否刷新 |
| 发现泄漏 | 通过版本/来源标记定位授权批次，收紧该批次 |

## 12. 开放问题

- 授权粒度：按用户、按内容类别，还是按单份文件？
- 是否需要在 UI 中显示"存在 L1 内容但未授权"（提升可发现性）还是完全隐藏（降低关注度）？
- 是否接受 Phase 1 长期存在（无代码改动，靠 GitHub 权限）？
- 申请审批的人力来自哪里，是否有拒绝标准？
- 私有资产（模型权重）如何分发：私有 NuGet 源、Release 资产，还是随内容仓库一并授权？

## 13. 风险认知（写入结论）

泄露是时间问题。任何"授权后可读"的内容最终都会离开授权范围。因此本方案的价值是：

- 收缩传播面（不是零）
- 明确规则与获取路径（替代"馋馋你们"式的玩笑）
- 让撤销与追溯成为可能

按"泄漏后能否定位与收窄"设计，而不是按"如何保证不泄漏"设计。
