# 委托机制分类提示词（P0）

本文件同时是**人工标注口径**与**模型分类提示词**。两者共用同一份定义，避免人工标准与模型标准不一致。修改本文件视作修改 P0 口径，重测前需重新标注受影响样本。

## 任务

输入是一条委托的名称、地区、描述文本，可能附带委托面板截图与现场截图。判断该委托属于哪一种**机制**，输出受控参数。

只看“这个委托要做什么”，不判断路线、坐标、具体打法。

## 机制枚举（封闭，禁止新增）

| mechanism | 定义 | 判定信号 | 典型动作 |
|---|---|---|---|
| `dialog` | 以对话推进：交谈、送物、打听、说服 | 描述主体是“与某人交谈/把某物交给某人/询问” | 多次对话、交付道具 |
| `combat` | 以战斗推进：击败敌人、清理营地、守住据点 | 出现“击败/消灭/驱除/清理” | 击杀目标、战斗结算 |
| `collect` | 在场景中采集或拾取若干个物件 | 出现“采集/收集/找到 N 个/拾取” | 跑点采集、交互拾取 |
| `escort` | 跟随或保护会移动的 NPC/物体 | 出现“护送/跟随/保护/带路” | 跟随移动、处理途中威胁 |
| `timed` | 核心约束是倒计时内到达或完成 | 描述强调“限时/在 X 时间内/赶在之前” | 限时跑点、限时送达 |
| `photo` | 使用留影机/相机对目标拍摄 | 出现“拍摄/留影/拍照/拍下” | 取景、拍照 |
| `music` | 乐器演奏或节奏小游戏 | 出现“演奏/弹奏/节奏/音律” | 按提示演奏 |
| `other` | 以上都不是，或信息不足无法判断 | 描述抽象、缺失关键动作 | 兜底 |

## 判定优先级

按“决定委托成败或耗时最长的环节”取**唯一**主导机制：

1. 护送途中需要战斗 → `escort`（`combat=true`），不归 `combat`。
2. 倒计时是主要压力，途中动作只是手段 → `timed`；否则按途中主要动作归类。
3. 需要先采集再交付 → 看哪段占主导；无法判断写 `other`。
4. 战斗只是可选的清场手段、成功不依赖它 → 不归 `combat`。
5. 同一委托含明显两段不同机制且无主次 → `other`，并在人工 `notes` 记录。

## 参数（受控取值）

| 参数 | 取值 | 说明 |
|---|---|---|
| `target` | `npc` / `enemy` / `object` / `place` / `unknown` | 主要交互对象 |
| `time_limit` | 整数秒，`0` 表示无限制 | 只在描述给出明确时限时填写，不推测 |
| `combat` | `true` / `false` | 是否需要战斗才能完成 |

## 置信度

`confidence` 取 0~1，表示“仅凭当前可见输入能确定机制的程度”：

- `>= 0.8`：描述直接给出动作关键词，几乎无歧义。
- `0.5 ~ 0.8`：需要结合截图或常识推断。
- `< 0.5`：信息不足或多种机制冲突。

`confidence < 0.5` 时仍须给出最可能的 mechanism；执行侧会按低置信度走兜底，不使用该结果硬跑。

## 输出格式

只输出一个 JSON 对象，不要解释、不要代码块以外的文字：

```json
{
  "mechanism": "escort",
  "confidence": 0.86,
  "params": { "target": "npc", "time_limit": 180, "combat": true },
  "evidence": "护送NPC到达指定地点，途中会遭遇敌人"
}
```

约束：

1. `mechanism` 必须是上表 8 个值之一。
2. 不得新增字段或自由文本字段；`evidence` 不超过 30 字。
3. `params` 必须三个键齐全，取值在受控集合内。
4. 描述与截图冲突时，以描述文本为准，并降低 `confidence`。
